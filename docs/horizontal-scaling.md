# Несколько машин

Код под это не переписан. Файл фиксирует, почему один процесс не масштабируется на несколько машин и что менять, когда это понадобится. Возвращаться сюда, а не выводить схему заново.

Пять горутин на машину — предел этой машины (CPU, память, одновременные клоны). Больше задач одновременно означает больше машин с тем же бинарём, а не больше горутин в одном процессе.

## Как устроено сейчас

Один процесс держит и HTTP, и воркеры.

- База — файл SQLite. Путь задаёт `SQLITE_PATH` (по умолчанию `data/analysis.db`). Соединение одно: `SetMaxOpenConns(1)`.
- `POST /api/v1/analysis` пишет строку `PENDING` и кладёт id в канал этого процесса (`worker.Pool`, буфер `QUEUE_SIZE`, по умолчанию 128). Пока канал полон, запрос ждёт.
- Воркеры читают только свой канал. Число воркеров — `WORKER_COUNT` (по умолчанию 2).
- Захват атомарный: `UPDATE analysis_tasks SET status = 'RUNNING' WHERE id = ? AND status = 'PENDING'`. Второй желающий получает ноль строк.
- При старте в канал возвращаются только `PENDING` (`ListPendingIDs`). `RUNNING` не трогается.
- Обычная остановка дожидается задачи, которую воркер уже взял. Убитый процесс, OOM или пропавшая машина оставляют задачу в `RUNNING`.
- Клон репозитория — временный каталог на этой машине. Результат и отчёт лежат в базе. Страница и `GET /api/v1/analysis/{id}` отвечают по id.
- Длительность — `updated_at` минус `created_at`. Эти поля для аренды не использовать.

## Проблема — решение

1. **Проблема:** база — файл SQLite на диске одной машины. Вторая машина его не видит и не может безопасно писать в тот же файл.
   **Решение:** одна общая база на все машины. Postgres подходит. Условный захват `UPDATE ... WHERE status = 'PENDING'` остаётся.

2. **Проблема:** очередь — канал в памяти процесса. Id задачи получает только тот процесс, который принял `POST`. Соседние машины этот id не видят.
   **Решение:** очередь — строки `PENDING` в общей базе. Воркер сам берёт следующую задачу одним запросом и метит её `RUNNING`. Канал в памяти для этого больше не нужен. Опрос раз в секунду-две для этой нагрузки достаточен. Отдельный брокер не обязателен.

3. **Проблема:** пока канал из 128 мест полон, `POST` ждёт именно этот процесс. Другие машины простаивают и эту очередь не разгружают.
   **Решение:** `POST` только записывает `PENDING` в общую базу и сразу возвращает id. Разбирать задачу может любая машина.

4. **Проблема:** если процесс убили, закончилась память или пропала машина, задача остаётся `RUNNING`. При старте в очередь возвращаются только `PENDING`, поэтому её никто больше не возьмёт. Это дыра уже на одной машине.
   **Решение:** аренда. Давно не обновлявшийся `RUNNING` снова становится `PENDING`, и его берёт другая машина. Аренда — отдельный факт: кто держит задачу и до какого момента. На длительность это не влияет: она по-прежнему считается как `updated_at` минус `created_at`.

5. **Проблема:** пять горутин берегут одну машину, но три машины по пять воркеров — это пятнадцать одновременных клонов и до пятнадцати запросов к модели. AI HUB уже отвечал 429 и `admission_queue_full` при меньшей нагрузке. Тот же упор ждут Git и сервис патчей.
   **Решение:** общий потолок на число `RUNNING` сразу по всем машинам. Иначе упор будет в AI HUB, Git и сервис патчей, а не в процессор.

6. **Проблема:** и ручки, и воркеры читают локальную базу своего процесса. Страница статуса и скачивание отчёта попадут на другую машину и не найдут задачу.
   **Решение:** все реплики читают и пишут одну базу. Перед ними один адрес. Ответить по id может любая машина.

## Что уже годится

- Условный захват по статусу `PENDING`.
- UUID задачи.
- Локальный клон. Общий том для репозиториев не нужен.
- Результат и отчёт в базе, не на диске воркера.
- Чтение задачи по id: любая реплика отвечает, если видит ту же базу.
- Один и тот же бинарь на каждой машине: HTTP и воркеры. Отдельный режим «только воркер» для первого шага не обязателен. Новая машина добавляет свои пять мест.

## Чего не делать

- Не класть файл SQLite на общий сетевой диск и не запускать на нём два писателя.
- Не оставлять канал в памяти вторым источником правды рядом с базой. Балансировщик будет засыпать одну машину, пока остальные простаивают.
- Не делить роли API и воркера раньше общей базы. Процесс, принявший `POST`, не должен быть единственным, кто имеет право выполнить задачу.
- Не поднимать `WORKER_COUNT` вместо новой машины, если упёрлись в CPU или память этой машины.
- Не увеличивать число машин без общего потолка на `RUNNING`: лимит AI HUB общий на все машины.

## В каком порядке делать

1. Общая база и тот же условный захват.
2. Воркер берёт следующую `PENDING` из базы, канал уходит.
3. `POST` только вставляет строку и возвращает id.
4. Аренда: протухший `RUNNING` возвращается в `PENDING`.
5. Общий потолок на число одновременных `RUNNING`.
6. Один адрес перед репликами.
