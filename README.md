# CVE analysis

Бэкенд принимает задачу на анализ Git-репозитория, сохраняет её в SQLite и обрабатывает пулом воркеров. В начале читается `dapp/README.md`, если он есть в корне клона: это заметки разработчиков, они попадают в отчёт и учитываются в выводе. Если файла нет, шаг пропускается.

Если в дереве нет ни одного `go.mod`, проект не на Go, но анализ не останавливается. Патч всё равно запрашивается, затем дерево ищется как `grep -rwn`, и вокруг совпадений сохраняются куски файлов. Когда в патче есть файлы, фразы берутся из diff: имена функций, строковые литералы изменённых строк и отличимые идентификаторы. Когда файлов нет, модель называет 5 фраз по описанию. `deadcode` для такого дерева не запускается. Ноль совпадений — уязвимость неприменима. Если совпадения есть, модель выбирает: применима, неприменима или неопределенна. Неопределенный вывод она обязана объяснить.

Если `go.mod` есть, анализ читает каждый из них. Для каждого файла, где указан `package_name`, сохраняются свои `verdict` и внутренний отчёт: есть ли рядом каталог `vendor`, и полный ответ `GET /cve/patch/{cve_id}`. Один запрос патча ждёт 30 секунд. Таймаут повторяется на 50 секунд и затем на 1 минуту; третий таймаут останавливает анализ. Если в `message` ответа есть `read: connection reset by peer` или `403`, следующая попытка снова идёт с 30 секунд и повторяется, пока не придёт патч или не кончится общий таймаут. В сообщении бывает только одна из этих причин. Файлы без пакета в результат не попадают.

Поле `report_md` в `GET /api/v1/analysis/{id}` — это не структура, а длинный текст. После вердикта модель получает весь внутренний отчёт и пишет журнал: что проверяли, в каком порядке, что нашли и почему вывод такой. Скачивание отдаёт тот же текст. В базе по-прежнему лежит структура, из которой журнал собран.

`package_name=root` не ищет `go.mod` и не смотрит `vendor`: каждый файл патча ищется от корня склонированного репозитория. Если имя пакета другое, а в патче есть пути файлов, те же пути дополнительно проверяются от корня. Совпадение сохраняется отдельным результатом. Явный `root` по-прежнему проверяет только корень.

`package_name=stdlib` — это стандартная библиотека Go, её нет в `require` и в `vendor`. Для каждого `go.mod` версия берётся из строки `toolchain`, а если там `local`, `default` или строки нет — из `go`. Номер из трёх чисел, как `go 1.22.5` или `toolchain go1.22.5`, качается как есть. Строка без патча тоже проверяется. Если её линейка совпадает с `GO_CURRENT_VERSION`, например `1.27.4`, анализ идёт этой версией, как если бы она стояла в `go.mod`. Другая линейка без патча, как `go 1.26`, берёт последнюю опубликованную патч-версию этой линейки. Если версию выбрать не удалось, модуль остаётся непроверенным. Исходники запрашивает уже установленный Go командой `go env GOROOT` с `GOTOOLCHAIN=go1.22.5` и оставляет их в кэше модулей. Если скачать не удалось, по версии уязвимость есть, а досягаемость не проверялась; Go из контейнера вместо скачанного не подставляется. Скачивание слот `deadcode` не занимает. Дальше `go list -deps` смотрит, импортирует ли программа пакет из патча: не импортирует — уязвимость неприменима и `deadcode` не запускается. Импортирует — один `go list` и один `deadcode` в каталоге модуля, оба с тем же `GOTOOLCHAIN` и с тем же слотом. `go.mod` нет — версия неизвестна, вывод неопределённый.

Для обычного пакета файл сначала ищется как `vendor/<модуль>/<путь из патча>`. Если его там нет, от пути патча отрезается самый длинный хвост пути модуля: патч `sdk/resource/host_id.go` при модуле `go.opentelemetry.io/otel/sdk` лежит в `vendor/go.opentelemetry.io/otel/sdk/resource/host_id.go`. Если путь патча содержит путь модуля целиком в середине, берётся остаток после него (`staging/src/k8s.io/client-go/rest/config.go`).

Сразу после получения патча из списка убираются `.md`, `.txt` и `_test.go`, без учёта регистра. Для `root`, `vendor` и стандартной библиотеки эти пути не ищутся и в отчёт не попадают. В `report_md.patch_files` остаются остальные файлы патча. `found: true` и `path` — файл есть в этом дереве, `found: false` — файла нет. Если все значения `false`, ни один файл патча в проекте не найден.

Для каждого `go.mod`, где пакет нашёлся, в `report_md.version` пишется версия из `require`. Для `root` версии нет. С `fixed_versions` она не сравнивается и анализ из-за неё не останавливается: если уязвимость есть в списке, версия уже считается уязвимой. На применимость версия не влияет.

Текст, собранный правилами анализа, хранится в `report_md.pre_verdict`. Поле `verdict` — профессиональный вывод: применима уязвимость или нет и почему. Процедуры в нём нет: ни поиска, ни совпадений, ни шаблона. Как шёл анализ, остаётся в журнале `report_md`. В промпт уходит весь внутренний отчёт и шаблон ситуации. Пакета нет ни в одном `go.mod` — анализ не останавливается: если файлы патча лежат в корне, берётся этот результат, иначе дерево ищется по описанию или по diff, как для проекта не на Go. Патч есть, но все файлы `false` — неприменима, уязвимого кода в дереве нет. Если файлы патча найдены, из diff берутся функции и `deadcode` проверяет, есть ли они среди недостижимых из `main`. Если функции в diff нет, а меняется тип или поле, проверяются функции модуля, которые этот тип используют. Неэкспортируемый тип ищется в своём пакете, экспортируемый — во всём модуле. Нет ни одной такой функции — уязвимость неприменима. Имя типа прочитать не удалось — досягаемость неизвестна. Запуск идёт от всех `package main` модуля. Если сборка падает, `main`, которые импортируют сломанный пакет, убираются, и проверка один раз повторяется на остальных, в том же слоте и в те же 4 минуты. Сломанный пакет из `vendor` считается так же: в нужную программу он не входит. Файл с уязвимой функцией, который сам не компилируется, оставляет досягаемость неизвестной. Повторно для каждого символа программа не поднимается. Одновременно запускаются не больше двух `deadcode`: остальные анализы ждут слот, и лимит в 4 минуты считается только после того, как слот получен. Не уложился — досягаемость остаётся непроверенной, и анализ идёт дальше к модели. Память каждого процесса — половина от трёх четвертей лимита cgroup, чтобы два запуска не складывались. При остановке гасится вся группа процессов, включая `go list`. Функция достижима — уязвимость применима, но только если патч не лежит в коде целиком. Неприменимость из-за уже применённого патча ставится, когда совпали все оставшиеся файлы кода и все фрагменты diff. Фрагмент совпал, когда в файле есть сама правка. Отступ, пробелы и табы, пустые строки и комментарии на это не влияют. Строка сравнивается токенами от начала и до последнего добавленного токена: хвост выражения, который патч не менял, может в этой версии уже быть другим. Если между добавленными строками стоит другой код, каждая ищется отдельно, поэтому импорт может стоять не между теми соседями, что в патче. Узнаваемая старая строка, например импорт или длинное условие, должна исчезнуть из файла. Обычная строка вроде `return nil`, `}` или короткого поля мешает, только когда она осталась рядом с найденной вставкой. Строки, добавленные подряд, остаются одним блоком. У одной правки ближайшая неизменённая строка сверху и снизу, если она в фрагменте есть, должна остаться рядом: между ней и правкой может лежать ещё до трёх строк. Короткая вставка вроде `total++` из-за такой же строки в другой функции не считается найденной. Код дальше этого окна фрагмент не отменяет и сам по себе его не подтверждает. Старая строка одной правки мешает, только когда она осталась в том же окне. Если фрагмент только удаляет код, этих строк в файле уже не должно быть. Файла, которого в дереве нет и который патч только правит, в этой сверке нет. Файл, созданный патчем с нуля, при отсутствии в дереве не даёт признать патч применённым. То же с функцией. Если в заголовке фрагмента названа функция, которой в файле нет, и патч её не создаёт, имя берётся из заголовка и фрагмент не считается. Если функция из заголовка в файле есть, а над правкой внутри фрагмента стоит другая строка func без плюса, имя берётся из неё: этой функции в файле нет — правка под ней не считается. Функция, которую патч создаёт с нуля, должна быть в коде. Если часть файлов кода уже содержит патч, а часть нет, в конец вердикта дописывается: «Патч частично применен, но в этих файлах патч не применен» и список этих файлов через запятую. Один несовпавший фрагмент или неразобранный diff оставляет уязвимость применимой. Если построчная сверка по файлу не дошла до 100 процентов, по каждому такому файлу уходит один запрос модели: несошедшиеся фрагменты с добавленным кодом и кусок файла. Кусок — функция из заголовка фрагмента. Если этой функции в файле уже нет, в кусок входят функции, которые фрагмент добавляет. Если имени функции в заголовке нет и фрагмент функцию не добавляет, остаются объявления до первой функции. В запросе нет счёта совпадений и нет готового вывода. Модель отвечает на файл целиком: видна ли попытка внести этот патч. Не каждый фрагмент обязан быть на месте, имена могут отличаться после предыдущих патчей, сомнение считается за «да». «Нет» — только когда попытки не видно. «Да» принимается, когда после него приведена строка из присланного куска. Совпадение каждого добавленного токена не требуется. Такое «да» зачитывает файл целиком. Фрагмент, который только удаляет код, модель не пересматривает. Правки функций, которых в файле нет, в запрос не попадают. Если после сверки все файлы кода сходятся, патч считается применённым целиком. Пустой, неразобранный ответ или ошибка модели оставляют прежний вывод. Если не совпал ни один фрагмент сразу в трёх или больше файлах кода, и в каждом из них фрагментов было два или больше, смысловая сверка не запускается, в том числе для файлов, где часть фрагментов уже совпала. Файл, в котором фрагменты не считались, в эти три не входит. Файл с одним ненайденным фрагментом в них тоже не входит: таких файлов спрашивают до четырёх. Если их больше четырёх, их оставляют построчной сверке, а файлы, где уже что-то совпало, всё равно спрашивают. Модель может счесть оставшуюся правку несущественной, если это время, дата, штамп генерации или версия в комментарии, и процитировать эту строку из diff. Условие, лимит, проверка или вызов так не проходят. Функция, которую патч удаляет и которой уже нет в файле, в deadcode не отправляется: отсутствие в списке недостижимого кода иначе читается как «функция живая». В конец полного отчёта дописывается пункт «Проверка применения патча»: проводилась ли сверка, целиком ли лёг патч, частично или diff не разобран, и как это повлияло на вывод. Если сверка не запускалась, там же написано почему. Все функции мертвы или не входят в программу — неприменима, уязвимый код недостижим. Если `deadcode` не запустился, в модуле нет `main` или из патча не удалось назвать ни функцию, ни тип, проверка не доведена и признак `uncertain`. Тип, который есть в дереве, но не используется кодом модуля, даёт `not_applicable`.

Модель ходит в OpenAI-совместимый endpoint. Проверка TLS-сертификата отключена: контур отдаёт свой сертификат.

Если в патче нет файлов, а пакет есть в `go.mod` и рядом лежит `vendor`, модель называет условие, без которого уязвимость не работает. Для обычной дыры это сам пакет. Для дыры в отдельной возможности это её путь импорта и вызов, например `google.golang.org/grpc/authz` и `authz.New`. Условие сверяется с зависимостями `package main`. Пакет входит в сборку и, когда дыра в отдельной возможности, код приложения её вызывает — уязвимость применима. В сборку не входит или возможность не вызывается — неприменима. Файлы внутри `vendor` самой библиотеки в плюс не идут. Неопределённо остаётся, только когда условие из описания не прочитано, в модуле нет `main` или список пакетов программы не собрался. Для дерева без такого модуля модель по-прежнему называет 5 фраз для `grep -rwn` по описанию. Фразы и совпадения пишутся в `report_md.grep`. На каждую фразу сохраняется не больше 5 строк, всего не больше 25, строка обрезается до 160 символов. Рядом, в `grep.excerpts`, лежит кусок файла вокруг совпадения: для Go это тело функции, но не больше 40 строк и 8 таких кусков на отчёт. После этого весь отчёт уходит модели ещё раз: она выбирает, применима уязвимость или нет. Каталог `.git` в поиск не входит.

Файл базы задаётся `SQLITE_PATH` и не удаляется при перезапуске. Задачи в статусе `PENDING` после старта снова ставятся в очередь.

## Запуск

Нужны Go 1.22 и `git`. Для проверки досягаемости нужен `deadcode` в `PATH`.

```bash
go install golang.org/x/tools/cmd/deadcode@v0.28.0
export PATH="$(go env GOPATH)/bin:$PATH"
go run ./cmd/server
```

`v0.28.0` собирается на Go 1.22. Каталог `$(go env GOPATH)/bin` должен быть в `PATH`, иначе анализ увидит файлы патча, но поле `reach.reachable` оставит пустым и не решит, что код недостижим.

Сервер слушает `:8741` и отвечает на запросы страницы с другого порта: браузеру отдаётся `Access-Control-Allow-Origin: *`. Форма ходит на тот же origin по пути `/api/v1/analysis`: перед страницей стоит прокси, который отдаёт этот путь на API. Копирование вердикта идёт через скрытое поле, потому что `navigator.clipboard` на обычном HTTP не работает. База создаётся в `data/analysis.db`. При старте читается файл `.env` в корне проекта. Уже заданные переменные окружения он не перезаписывает. Сам файл в git не входит: в нём может лежать `GIT_TOKEN`.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `HTTP_ADDR` | `:8741` | Адрес HTTP |
| `SQLITE_PATH` | `data/analysis.db` | Файл SQLite |
| `WORKER_COUNT` | `2` | Число воркеров |
| `GIT_TIMEOUT` | `2m` | Общий таймаут клона и всего анализа |
| `GIT_TOKEN` | пусто | Токен для clone по HTTPS. Адрес приводится к виду `https://хост/группа/проект.git`. Пароль — этот токен, логин — `oauth2`, а для `github.com` — `x-access-token`. Подходит и `https://...`, и `git@хост:группа/проект.git`: SSH-адрес при наличии токена клонируется по HTTPS. Без токена SSH-адрес не меняется. Тот же токен читает подсказки проектов и веток |
| `GIT_SUGGEST_ROOT` | `https://git.slo/dapp` | Группа GitLab для подсказок в форме запуска. Пустое значение подсказки выключает |
| `CVE_PATCH_BASE` | `http://d49.dev.k8s:8080` | База ручки `GET /cve/patch/{cve_id}` |
| `AI_BASE_URL` | пусто | Полный URL чата модели. Пустой URL роняет задачу на шаге вердикта |
| `AI_TOKEN` | пусто | Bearer-токен модели |
| `AI_MODEL` | пусто | Модель по умолчанию. Новый анализ начинает с неё, в запросе можно передать другую `model` |
| `GO_CURRENT_VERSION` | пусто | Актуальный Go текущей линейки, например `1.27.4`. Для `package_name=stdlib` строка `go 1.27` проверяется этой версией |
| `WEB_BASE_URL` | пусто | Публичный адрес страницы без завершающего `/`. Редирект `GET /api/v1/analysis/open` ведёт на `{WEB_BASE_URL}/analysis/{id}`. Пустое значение — тот же хост и путь `/analysis/{id}` |

## API

Swagger UI открывается по `GET /api/v1/analysis/docs/`, спецификация — `GET /api/v1/analysis/openapi.json`. В Swagger можно нажать Try it out: создать задачу, взять `id` из ответа и тем же экраном запросить статус и результат. Страница и Swagger живут на одном пути `/api/v1/analysis`, поэтому прокси перед формой должен отдавать весь этот префикс, включая `/docs/` и `/openapi.json`.

`GET /api/v1/analysis/default-model` — `{"model":"..."}`, имя из `AI_MODEL`. Токен модели наружу не отдаётся.

`GET /api/v1/analysis/go-version` — `{"version":"1.27.4"}` из `GO_CURRENT_VERSION`. Пустая строка значит, что переменная не задана. Уже сделанный анализ эту ручку не читает: версия тулчейна лежит в отчёте модуля, в поле `go_version`, и остаётся той, которой шёл этот запуск.

`GET /api/v1/analysis/models` — `{"models":["..."]}`. Сервер ходит в `GET /v1/models` того же контура, что и чат, с `AI_TOKEN`.

`GET /api/v1/analysis/projects?q=` — до 20 проектов группы `GIT_SUGGEST_ROOT`, вместе с вложенными группами. В ответе путь, адрес `https://хост/группа/проект.git` и ветка по умолчанию. `GET /api/v1/analysis/branches?component_url=&q=` — до 20 веток этого проекта. Чужой адрес, пустой токен или молчащий GitLab дают `{"items":[]}`. Форма запуска показывает это под полями ссылки и ветки и не мешает вписать свой адрес.

`POST /api/v1/analysis` — создать задачу, ответ `202` и `{"id":"..."}`. Поле `model` необязательное: пустое значит модель из `AI_MODEL`. Выбранное имя сохраняется в задаче и уходит в запросы к модели. Если AI HUB отвечает `429` с `admission_queue_full`, тот же запрос сразу повторяется моделью `Qwen/Qwen3.6-35B-A3B`, а если очередь полная и у неё — `GigaChat-2-Pro`. Анализ продолжается с этого шага, клон заново не качается. В задаче и в журнале остаётся модель, которая дописала вывод. Другие ошибки модели резерв не включают.

`GET /api/v1/analysis/open?component_url=...&branch=...&cve_id=...&package_name=...` — ссылка для кнопки на дашборде. Браузер открывает её и получает `302` на страницу `/analysis/{id}`. Сервер берёт самый новый анализ с этими четырьмя полями. Если такого нет, создаёт анализ с моделью из `AI_MODEL`, ставит его в очередь и редиректит уже на новый. Статус не важен: откроется и готовый анализ, и ещё идущий, и упавший. Строки сравниваются точно, пробелы по краям отбрасываются. Алиас и CVE ID — разные значения. Ссылку открывают на том хосте, где живёт страница. Если API отвечает с другого хоста, задайте `WEB_BASE_URL`.

`GET /api/v1/analysis/status?component_url=...&branch=...&cve_id=...&package_name=...` — кнопка «Проверить статус». Те же четыре параметра. Анализ не создаётся. Ответ `200` и `{"result":"..."}`. Шесть значений: `applicable` (применима), `not_applicable` (неприменима), `uncertain` (неопределенно), `not_started` (такой четвёрки нет), `in_progress` (в очереди или выполняется), `failed` (проверка упала). Берётся самый новый анализ. Упавший не маскируется под `uncertain`. Если параметра не хватает, ответ `400`.

```bash
curl -s -X POST localhost:8741/api/v1/analysis \
  -H 'Content-Type: application/json' \
  -d '{"component_url":"https://github.com/golang/example","branch":"master","cve_id":"CVE-2024-0001","package_name":"example"}'
```

`GET /api/v1/analysis?limit=10&offset=0&status=PENDING` — `{"items":[...],"total":N}`. В `items` нет `verdict` и `report_md`. У каждой задачи есть `duration_ms` и `applicability`. `total` — сколько таких записей в базе под тем же фильтром, без учёта `limit` и `offset`. Кроме `status` в запрос можно передать `component_url`, `branch`, `cve_id`, `package_name` и `applicability`. Пустое поле условие не добавляет. `branch`, `cve_id` и `package_name` сравниваются целиком, без учёта регистра. `component_url` ищется по вхождению, тоже без учёта регистра. `applicability` — `applicable`, `not_applicable` или `uncertain`, и только у завершённого анализа: упавшая задача в эту выборку не входит. Неизвестное значение даёт `400`.

`duration_ms` — сколько миллисекунд шёл сам анализ, без ожидания в очереди. Старт пишется, когда воркер берёт задачу. Для завершённой, упавшей и остановленной задачи конец — `updated_at`. Пока задача `RUNNING`, это текущее время минус старт. Пока она `PENDING`, поле `null`. У задач, созданных до появления старта, остаётся прежняя разница `updated_at` минус `created_at`.

`applicability` — один признак на всю задачу: `applicable` (уязвимость применима), `not_applicable` (неприменима) или `uncertain` (неопределенно). Пока анализа нет, поле `null`. У `FAILED` оно `uncertain`. Если модулей несколько, достаточно одного `applicable`, чтобы задача стала `applicable`. `not_applicable` ставится, когда применимых нет и хотя бы один модуль неприменим, а все `uncertain` неопределённы только потому, что рядом с их `go.mod` нет `vendor`. Если `vendor` нет ни у одного модуля, задача остаётся `uncertain`. Неопределённость по другой причине тоже оставляет задачу `uncertain`.

`POST /api/v1/analysis/{id}/review` — оценка этого запуска. Тело `{"rating":5,"review":"вердикт верный"}`. `rating` от 1 до 5: 5 — вердикт верный, 1 — неверный. `null` убирает звёзды. Пустой `review` убирает текст. Оба пустые снимают анализ со страницы отзывов. Повтор заменяет предыдущую оценку. Новый запуск тех же четырёх полей начинается без оценки.

`GET /api/v1/analysis/reviews?limit=10&offset=0` — анализы, у которых есть звёзды или текст. В строке оценка, отзыв и четыре параметра. `average` — средняя оценка только по звёздам. Текст без звёзд в среднее не входит. Если звёзд нет, `average` равен `null`.

`GET /api/v1/analysis/{id}` — полная задача. У каждого модуля свой `applicability` с теми же тремя значениями и `report_md` — строка с журналом анализа. `duration_ms` и `applicability` задачи те же, что в списке. У ошибки рядом с `error_msg` есть `error_source` и `error_hint`: кто виноват, по тексту, который сервис уже записал. Модель для этого не вызывается. `AI HUB` — шлюз модели, `Сервис патчей` — ручка патча, `Git` — клон репозитория, остальное — `CVE Patch Analyzer`.

Клонируется сразу запрошенная ветка, один коммит: `git clone --single-branch --depth 1 --branch`. Отдельного checkout нет. Если сертификат сервера подписан неизвестным издателем, как у внутреннего GitLab, тот же клон повторяется без проверки сертификата: до токена запрос в этом случае не доходит.

Если анализ обрывается, в том числе по дедлайну в 15 минут, в ошибке остаётся этап остановки и сколько `go.mod` уже найдено. Поле `go_mod_count` то же число, `stop_stage` — фраза для страницы. Ноль обращений к модели значит, что до модели дело не дошло: время ушло на поиск модулей, патч или проверку достижимости.

Там же четыре поля: `clone_ms`, `ai_calls`, `ai_min_ms`, `ai_max_ms`. `clone_ms` — сколько миллисекунд заняло клонирование, в том числе если клон оборвался. Остальные три — число обращений к модели и самое короткое и самое долгое ожидание ответа. Неудачный ответ тоже считается. Пока задача в очереди, счётчик ноль, а времена `null`. После завершения, ошибки и обрыва по дедлайну цифры остаются на странице: если до модели дело не дошло, обращений ноль, а времена ответа `null`. Время клона появляется сразу, как клон закончился, даже если анализ ещё идёт.

`POST /api/v1/analysis/{id}/cancel` — остановить анализ в очереди или в работе. Статус становится `FAILED`, `error_msg` — «Остановлен принудительно нажатием на кнопку "Остановить анализ"». Это не сбой сервиса, поэтому `error_source` пустой. Текущая работа прерывается. Уже завершённую или уже упавшую задачу ручка не меняет и отвечает `409`.

`GET /api/v1/analysis/{id}/report` — тот же журнал текстом, только для `COMPLETED`.
