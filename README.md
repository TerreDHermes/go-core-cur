# CVE analysis

Бэкенд принимает задачу на анализ Git-репозитория, сохраняет её в SQLite и обрабатывает пулом воркеров. В начале читается `dapp/README.md`, если он есть в корне клона: это заметки разработчиков, они попадают в отчёт и учитываются в выводе. Если файла нет, шаг пропускается.

Если в дереве нет ни одного `go.mod`, проект не на Go, но анализ не останавливается. Патч всё равно запрашивается, затем дерево ищется как `grep -rwn`, и вокруг совпадений сохраняются куски файлов. Когда в патче есть файлы, фразы берутся из diff: имена функций, строковые литералы изменённых строк и отличимые идентификаторы. Когда файлов нет, модель называет 5 фраз по описанию. `deadcode` для такого дерева не запускается. Ноль совпадений — уязвимость неприменима. Если совпадения есть, модель выбирает: применима, неприменима или неопределенна. Неопределенный вывод она обязана объяснить.

Если `go.mod` есть, анализ читает каждый из них. Для каждого файла, где указан `package_name`, сохраняются свои `verdict` и внутренний отчёт: есть ли рядом каталог `vendor`, и полный ответ `GET /cve/patch/{cve_id}`. Если в `message` ответа есть `read: connection reset by peer`, запрос повторяется, пока не придёт патч или не кончится таймаут. Файлы без пакета в результат не попадают.

Поле `report_md` в `GET /api/v1/analysis/{id}` — это не структура, а длинный текст. После вердикта модель получает весь внутренний отчёт и пишет журнал: что проверяли, в каком порядке, что нашли и почему вывод такой. Скачивание отдаёт тот же текст. В базе по-прежнему лежит структура, из которой журнал собран.

`package_name=root` не ищет `go.mod` и не смотрит `vendor`: каждый файл патча ищется от корня склонированного репозитория.

Для обычного пакета файл сначала ищется как `vendor/<модуль>/<путь из патча>`. Если его там нет, от пути патча отрезается самый длинный хвост пути модуля: патч `sdk/resource/host_id.go` при модуле `go.opentelemetry.io/otel/sdk` лежит в `vendor/go.opentelemetry.io/otel/sdk/resource/host_id.go`. Если путь патча содержит путь модуля целиком в середине, берётся остаток после него (`staging/src/k8s.io/client-go/rest/config.go`).

В `report_md.patch_files` перечислены все файлы патча. `found: true` и `path` — файл есть в этом дереве, `found: false` — файла нет. Если все значения `false`, ни один файл патча в проекте не найден.

Для каждого `go.mod`, где пакет нашёлся, в `report_md.version` пишется версия из `require`. Для `root` версии нет. С `fixed_versions` она не сравнивается и анализ из-за неё не останавливается: если уязвимость есть в списке, версия уже считается уязвимой. На применимость версия не влияет.

Текст, собранный правилами анализа, хранится в `report_md.pre_verdict`. Поле `verdict` — профессиональный вывод: применима уязвимость или нет и почему. Процедуры в нём нет: ни поиска, ни совпадений, ни шаблона. Как шёл анализ, остаётся в журнале `report_md`. В промпт уходит весь внутренний отчёт и шаблон ситуации. Пакета нет ни в одном `go.mod` — неприменима, дерево не ищется. Патч есть, но все файлы `false` — неприменима, уязвимого кода в дереве нет. Если файлы патча найдены, из diff берутся функции и `deadcode -whylive` проверяет путь от `main`. Функция достижима — уязвимость применима. Все функции мертвы или не входят в программу — неприменима, уязвимый код недостижим. Если `deadcode` не запустился, в модуле нет `main` или функцию из diff выделить не удалось, проверка не доведена и признак `uncertain`.

Модель ходит в OpenAI-совместимый endpoint. Проверка TLS-сертификата отключена: контур отдаёт свой сертификат.

Если в патче нет файлов, модель сначала называет 5 фраз для `grep -rwn` по описанию. Фразы и совпадения пишутся в `report_md.grep`. На каждую фразу сохраняется не больше 5 строк, всего не больше 25, строка обрезается до 160 символов. Рядом, в `grep.excerpts`, лежит кусок файла вокруг совпадения: для Go это тело функции, но не больше 40 строк и 8 таких кусков на отчёт. После этого весь отчёт уходит модели ещё раз: она выбирает, применима уязвимость или нет. Каталог `.git` в поиск не входит.

Файл базы задаётся `SQLITE_PATH` и не удаляется при перезапуске. Задачи в статусе `PENDING` после старта снова ставятся в очередь.

## Запуск

Нужны Go 1.22 и `git`. Для проверки досягаемости нужен `deadcode` в `PATH`.

```bash
go install golang.org/x/tools/cmd/deadcode@v0.28.0
export PATH="$(go env GOPATH)/bin:$PATH"
go run ./cmd/server
```

`v0.28.0` собирается на Go 1.22. Каталог `$(go env GOPATH)/bin` должен быть в `PATH`, иначе анализ увидит файлы патча, но поле `reach.reachable` оставит пустым и не решит, что код недостижим.

Сервер слушает `:8741`. База создаётся в `data/analysis.db`. При старте читается файл `.env` в корне проекта. Уже заданные переменные окружения он не перезаписывает. Сам файл в git не входит: в нём может лежать `GIT_TOKEN`.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `HTTP_ADDR` | `:8741` | Адрес HTTP |
| `SQLITE_PATH` | `data/analysis.db` | Файл SQLite |
| `WORKER_COUNT` | `2` | Число воркеров |
| `GIT_TIMEOUT` | `2m` | Таймаут clone и поиска |
| `GIT_TOKEN` | пусто | Токен для приватного HTTPS-репозитория. Без него чужой приватный репозиторий отвечает 403 |
| `CVE_PATCH_BASE` | `http://d49.dev.k8s:8080` | База ручки `GET /cve/patch/{cve_id}` |
| `AI_BASE_URL` | пусто | Полный URL чата модели. Пустой URL роняет задачу на шаге вердикта |
| `AI_TOKEN` | пусто | Bearer-токен модели |
| `AI_MODEL` | пусто | Имя модели в теле запроса |

## API

`POST /api/v1/analysis` — создать задачу, ответ `202` и `{"id":"..."}`.

```bash
curl -s -X POST localhost:8741/api/v1/analysis \
  -H 'Content-Type: application/json' \
  -d '{"component_url":"https://github.com/golang/example","branch":"master","cve_id":"CVE-2024-0001","package_name":"example"}'
```

`GET /api/v1/analysis?limit=10&offset=0&status=PENDING` — `{"items":[...],"total":N}`. В `items` нет `verdict` и `report_md`. У каждой задачи есть `duration_ms` и `applicability`. `total` — сколько таких записей в базе под тем же фильтром `status` (без фильтра — все задачи), без учёта `limit` и `offset`.

`duration_ms` — `updated_at` минус `created_at`, в миллисекундах. Это сколько задача живёт с момента запроса клиента до последнего изменения статуса.

`applicability` — один признак на всю задачу: `applicable` (уязвимость применима), `not_applicable` (неприменима) или `uncertain` (неопределенно). Пока анализа нет, поле `null`. У `FAILED` оно `uncertain`. Если модулей несколько, достаточно одного `applicable`, чтобы задача стала `applicable`. Если применимых нет, но есть `uncertain`, задача `uncertain`. `not_applicable` ставится, только когда такой вывод у каждого модуля.

`GET /api/v1/analysis/{id}` — полная задача. У каждого модуля свой `applicability` с теми же тремя значениями и `report_md` — строка с журналом анализа. `duration_ms` и `applicability` задачи те же, что в списке.

`GET /api/v1/analysis/{id}/report` — тот же журнал текстом, только для `COMPLETED`.
