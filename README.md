# CVE analysis

Бэкенд принимает задачу на анализ Git-репозитория, сохраняет её в SQLite и обрабатывает пулом воркеров. В начале читается `dapp/README.md`, если он есть в корне клона: это заметки разработчиков, они попадают в отчёт и учитываются в выводе. Если файла нет, шаг пропускается.

Если в дереве нет ни одного `go.mod`, проект не на Go, но анализ не останавливается. Патч всё равно запрашивается, затем дерево ищется как `grep -rwn`, и вокруг совпадений сохраняются куски файлов. Когда в патче есть файлы, фразы берутся из diff: имена функций, строковые литералы изменённых строк и отличимые идентификаторы. Когда файлов нет, модель называет 5 фраз по описанию. `deadcode` для такого дерева не запускается. Ноль совпадений — уязвимость неприменима. Если совпадения есть, модель выбирает: применима, неприменима или неопределенна. Неопределенный вывод она обязана объяснить.

Если `go.mod` есть, анализ читает каждый из них. Для каждого файла, где указан `package_name`, сохраняются свои `verdict` и внутренний отчёт: есть ли рядом каталог `vendor`, и полный ответ `GET /cve/patch/{cve_id}`. Если в `message` ответа есть `read: connection reset by peer`, запрос повторяется, пока не придёт патч или не кончится таймаут. Файлы без пакета в результат не попадают.

Поле `report_md` в `GET /api/v1/analysis/{id}` — это не структура, а длинный текст. После вердикта модель получает весь внутренний отчёт и пишет журнал: что проверяли, в каком порядке, что нашли и почему вывод такой. Скачивание отдаёт тот же текст. В базе по-прежнему лежит структура, из которой журнал собран.

`package_name=root` не ищет `go.mod` и не смотрит `vendor`: каждый файл патча ищется от корня склонированного репозитория. Если имя пакета другое, а в патче есть пути файлов, те же пути дополнительно проверяются от корня. Совпадение сохраняется отдельным результатом. Явный `root` по-прежнему проверяет только корень.

`package_name=stdlib` — это стандартная библиотека Go, её нет в `require` и в `vendor`. Для каждого `go.mod` версия берётся из строки `toolchain`, а если там `local`, `default` или строки нет — из `go`. Нужен номер патча из трёх чисел, как `go 1.22.5` или `toolchain go1.22.5`. Строка `go 1.22` этот модуль не проверяет: уровень патча не закреплён. Исходники запрашивает уже установленный Go командой `go env GOROOT` с `GOTOOLCHAIN=go1.22.5` и оставляет их в кэше модулей. Если скачать не удалось, по версии уязвимость есть, а досягаемость не проверялась; Go из контейнера вместо скачанного не подставляется. Скачивание слот `deadcode` не занимает. Дальше `go list -deps` смотрит, импортирует ли программа пакет из патча: не импортирует — уязвимость неприменима и `deadcode` не запускается. Импортирует — один `go list` и один `deadcode` в каталоге модуля, оба с тем же `GOTOOLCHAIN` и с тем же слотом. `go.mod` нет — версия неизвестна, вывод неопределённый.

Для обычного пакета файл сначала ищется как `vendor/<модуль>/<путь из патча>`. Если его там нет, от пути патча отрезается самый длинный хвост пути модуля: патч `sdk/resource/host_id.go` при модуле `go.opentelemetry.io/otel/sdk` лежит в `vendor/go.opentelemetry.io/otel/sdk/resource/host_id.go`. Если путь патча содержит путь модуля целиком в середине, берётся остаток после него (`staging/src/k8s.io/client-go/rest/config.go`).

В `report_md.patch_files` перечислены все файлы патча. `found: true` и `path` — файл есть в этом дереве, `found: false` — файла нет. Если все значения `false`, ни один файл патча в проекте не найден.

Для каждого `go.mod`, где пакет нашёлся, в `report_md.version` пишется версия из `require`. Для `root` версии нет. С `fixed_versions` она не сравнивается и анализ из-за неё не останавливается: если уязвимость есть в списке, версия уже считается уязвимой. На применимость версия не влияет.

Текст, собранный правилами анализа, хранится в `report_md.pre_verdict`. Поле `verdict` — профессиональный вывод: применима уязвимость или нет и почему. Процедуры в нём нет: ни поиска, ни совпадений, ни шаблона. Как шёл анализ, остаётся в журнале `report_md`. В промпт уходит весь внутренний отчёт и шаблон ситуации. Пакета нет ни в одном `go.mod` — анализ не останавливается: если файлы патча лежат в корне, берётся этот результат, иначе дерево ищется по описанию или по diff, как для проекта не на Go. Патч есть, но все файлы `false` — неприменима, уязвимого кода в дереве нет. Если файлы патча найдены, из diff берутся функции и один запуск `deadcode` на модуль проверяет, есть ли они среди недостижимых из `main`. Повторно для каждого символа программа не поднимается. Одновременно запускаются не больше двух `deadcode`: остальные анализы ждут слот, и лимит в 4 минуты считается только после того, как слот получен. Не уложился — досягаемость остаётся непроверенной, и анализ идёт дальше к модели. Память каждого процесса — половина от трёх четвертей лимита cgroup, чтобы два запуска не складывались. При остановке гасится вся группа процессов, включая `go list`. Функция достижима — уязвимость применима, но только если патч не лежит в коде целиком. Неприменимость из-за уже применённого патча ставится, когда совпали все файлы кода и все фрагменты diff. Файлы `_test.go` в эту сверку не входят. Если часть файлов кода уже содержит патч, а часть нет, в конец вердикта дописывается: «Патч частично применен, но в этих файлах патч не применен» и список этих файлов через запятую. Один несовпавший фрагмент или неразобранный diff оставляет уязвимость применимой. В конец полного отчёта дописывается пункт «Проверка применения патча»: проводилась ли сверка, целиком ли лёг патч, частично или diff не разобран, и как это повлияло на вывод. Если сверка не запускалась, там же написано почему. Все функции мертвы или не входят в программу — неприменима, уязвимый код недостижим. Если `deadcode` не запустился, в модуле нет `main` или функцию из diff выделить не удалось, проверка не доведена и признак `uncertain`.

Модель ходит в OpenAI-совместимый endpoint. Проверка TLS-сертификата отключена: контур отдаёт свой сертификат.

Если в патче нет файлов, модель сначала называет 5 фраз для `grep -rwn` по описанию. Фразы и совпадения пишутся в `report_md.grep`. На каждую фразу сохраняется не больше 5 строк, всего не больше 25, строка обрезается до 160 символов. Рядом, в `grep.excerpts`, лежит кусок файла вокруг совпадения: для Go это тело функции, но не больше 40 строк и 8 таких кусков на отчёт. После этого весь отчёт уходит модели ещё раз: она выбирает, применима уязвимость или нет. Каталог `.git` в поиск не входит.

Файл базы задаётся `SQLITE_PATH` и не удаляется при перезапуске. Задачи в статусе `PENDING` после старта снова ставятся в очередь.

## Запуск

Нужны Go 1.22 и `git`. Для проверки досягаемости нужен `deadcode` в `PATH`.

```bash
go install golang.org/x/tools/cmd/deadcode@v0.28.0
export PATH="$(go env GOPATH)/bin:$PATH"
go run ./cmd/server
```

`v0.28.0` собирается на Go 1.22. Каталог `$(go env GOPATH)/bin` должен быть в `PATH`, иначе анализ увидит файлы патча, но поле `reach.reachable` оставит пустым и не решит, что код недостижим.

Сервер слушает `:8741` и отвечает на запросы страницы с другого порта: браузеру отдаётся `Access-Control-Allow-Origin: *`. Форма ходит на тот же origin по пути `/api/v1/analysis`: перед страницей стоит прокси, который отдаёт этот путь на API. Копирование вердикта идёт через скрытое поле, потому что `navigator.clipboard` на обычном HTTP не работает. База создаётся в `data/analysis.db`. При старте читается файл `.env` в корне проекта. Уже заданные переменные окружения он не перезаписывает. Сам файл в git не входит: в нём может лежать `GIT_TOKEN`.

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `HTTP_ADDR` | `:8741` | Адрес HTTP |
| `SQLITE_PATH` | `data/analysis.db` | Файл SQLite |
| `WORKER_COUNT` | `2` | Число воркеров |
| `GIT_TIMEOUT` | `2m` | Общий таймаут клона и всего анализа |
| `GIT_TOKEN` | пусто | Токен для clone по HTTPS. Адрес приводится к виду `https://хост/группа/проект.git`. Пароль — этот токен, логин — `oauth2`, а для `github.com` — `x-access-token`. Подходит и `https://...`, и `git@хост:группа/проект.git`: SSH-адрес при наличии токена клонируется по HTTPS. Без токена SSH-адрес не меняется |
| `CVE_PATCH_BASE` | `http://d49.dev.k8s:8080` | База ручки `GET /cve/patch/{cve_id}` |
| `AI_BASE_URL` | пусто | Полный URL чата модели. Пустой URL роняет задачу на шаге вердикта |
| `AI_TOKEN` | пусто | Bearer-токен модели |
| `AI_MODEL` | пусто | Модель по умолчанию. Новый анализ начинает с неё, в запросе можно передать другую `model` |
| `WEB_BASE_URL` | пусто | Публичный адрес страницы без завершающего `/`. Редирект `GET /api/v1/analysis/open` ведёт на `{WEB_BASE_URL}/analysis/{id}`. Пустое значение — тот же хост и путь `/analysis/{id}` |

## API

Swagger UI открывается по `GET /api/v1/analysis/docs/`, спецификация — `GET /api/v1/analysis/openapi.json`. В Swagger можно нажать Try it out: создать задачу, взять `id` из ответа и тем же экраном запросить статус и результат. Страница и Swagger живут на одном пути `/api/v1/analysis`, поэтому прокси перед формой должен отдавать весь этот префикс, включая `/docs/` и `/openapi.json`.

`GET /api/v1/analysis/default-model` — `{"model":"..."}`, имя из `AI_MODEL`. Токен модели наружу не отдаётся.

`GET /api/v1/analysis/models` — `{"models":["..."]}`. Сервер ходит в `GET /v1/models` того же контура, что и чат, с `AI_TOKEN`.

`POST /api/v1/analysis` — создать задачу, ответ `202` и `{"id":"..."}`. Поле `model` необязательное: пустое значит модель из `AI_MODEL`. Выбранное имя сохраняется в задаче и уходит в запросы к модели. Если AI HUB отвечает `429` с `admission_queue_full`, тот же запрос сразу повторяется моделью `Qwen/Qwen3.6-35B-A3B`, а если очередь полная и у неё — `GigaChat-2-Pro`. Анализ продолжается с этого шага, клон заново не качается. В задаче и в журнале остаётся модель, которая дописала вывод. Другие ошибки модели резерв не включают.

`GET /api/v1/analysis/open?component_url=...&branch=...&cve_id=...&package_name=...` — ссылка для кнопки на дашборде. Браузер открывает её и получает `302` на страницу `/analysis/{id}`. Сервер берёт самый новый анализ с этими четырьмя полями. Если такого нет, создаёт анализ с моделью из `AI_MODEL`, ставит его в очередь и редиректит уже на новый. Статус не важен: откроется и готовый анализ, и ещё идущий, и упавший. Строки сравниваются точно, пробелы по краям отбрасываются. Алиас и CVE ID — разные значения. Ссылку открывают на том хосте, где живёт страница. Если API отвечает с другого хоста, задайте `WEB_BASE_URL`.

`GET /api/v1/analysis/status?component_url=...&branch=...&cve_id=...&package_name=...` — кнопка «Проверить статус». Те же четыре параметра. Анализ не создаётся. Ответ `200` и `{"result":"..."}`. Шесть значений: `applicable` (применима), `not_applicable` (неприменима), `uncertain` (неопределенно), `not_started` (такой четвёрки нет), `in_progress` (в очереди или выполняется), `failed` (проверка упала). Берётся самый новый анализ. Упавший не маскируется под `uncertain`. Если параметра не хватает, ответ `400`.

```bash
curl -s -X POST localhost:8741/api/v1/analysis \
  -H 'Content-Type: application/json' \
  -d '{"component_url":"https://github.com/golang/example","branch":"master","cve_id":"CVE-2024-0001","package_name":"example"}'
```

`GET /api/v1/analysis?limit=10&offset=0&status=PENDING` — `{"items":[...],"total":N}`. В `items` нет `verdict` и `report_md`. У каждой задачи есть `duration_ms` и `applicability`. `total` — сколько таких записей в базе под тем же фильтром `status` (без фильтра — все задачи), без учёта `limit` и `offset`.

`duration_ms` — сколько миллисекунд шёл сам анализ, без ожидания в очереди. Старт пишется, когда воркер берёт задачу. Для завершённой, упавшей и остановленной задачи конец — `updated_at`. Пока задача `RUNNING`, это текущее время минус старт. Пока она `PENDING`, поле `null`. У задач, созданных до появления старта, остаётся прежняя разница `updated_at` минус `created_at`.

`applicability` — один признак на всю задачу: `applicable` (уязвимость применима), `not_applicable` (неприменима) или `uncertain` (неопределенно). Пока анализа нет, поле `null`. У `FAILED` оно `uncertain`. Если модулей несколько, достаточно одного `applicable`, чтобы задача стала `applicable`. Если применимых нет, но есть `uncertain`, задача `uncertain`. `not_applicable` ставится, только когда такой вывод у каждого модуля.

`GET /api/v1/analysis/{id}` — полная задача. У каждого модуля свой `applicability` с теми же тремя значениями и `report_md` — строка с журналом анализа. `duration_ms` и `applicability` задачи те же, что в списке. У ошибки рядом с `error_msg` есть `error_source` и `error_hint`: кто виноват, по тексту, который сервис уже записал. Модель для этого не вызывается. `AI HUB` — шлюз модели, `Сервис патчей` — ручка патча, `Git` — клон репозитория, остальное — `CVE Patch Analyzer`.

Клонируется сразу запрошенная ветка, один коммит: `git clone --single-branch --depth 1 --branch`. Отдельного checkout нет. Если сертификат сервера подписан неизвестным издателем, как у внутреннего GitLab, тот же клон повторяется без проверки сертификата: до токена запрос в этом случае не доходит.

Если анализ обрывается, в том числе по дедлайну в 15 минут, в ошибке остаётся этап остановки и сколько `go.mod` уже найдено. Поле `go_mod_count` то же число, `stop_stage` — фраза для страницы. Ноль обращений к модели значит, что до модели дело не дошло: время ушло на поиск модулей, патч или проверку достижимости.

Там же четыре поля: `clone_ms`, `ai_calls`, `ai_min_ms`, `ai_max_ms`. `clone_ms` — сколько миллисекунд заняло клонирование, в том числе если клон оборвался. Остальные три — число обращений к модели и самое короткое и самое долгое ожидание ответа. Неудачный ответ тоже считается. Пока задача в очереди, счётчик ноль, а времена `null`. После завершения, ошибки и обрыва по дедлайну цифры остаются на странице: если до модели дело не дошло, обращений ноль, а времена ответа `null`. Время клона появляется сразу, как клон закончился, даже если анализ ещё идёт.

`POST /api/v1/analysis/{id}/cancel` — остановить анализ в очереди или в работе. Статус становится `FAILED`, `error_msg` — «Остановлен принудительно нажатием на кнопку "Остановить анализ"». Это не сбой сервиса, поэтому `error_source` пустой. Текущая работа прерывается. Уже завершённую или уже упавшую задачу ручка не меняет и отвечает `409`.

`GET /api/v1/analysis/{id}/report` — тот же журнал текстом, только для `COMPLETED`.
